物理 GPU: 0, 1, 2, 3

这是第一次真机测试最关键的参数之一。
G0.5 一次模型推理通常可以预测一串未来动作，例如：
第 1 步、第 2 步、第 3 步……第 32 步
服务端会缓存这串动作，按控制周期一条一条发给 client。
--action_steps 决定“做几步后重新拍相机、读关节、跑一次模型”。
设置	行为
1	每执行一个动作，都重新发送最新图像和关节状态，再推理一次
4	一次推理后连续使用 4 步缓存动作
16	连续使用 16 步缓存动作
32	连续使用 32 步缓存动作

当 action_steps=1 时：
相机/状态 → 模型 → 第 1 个动作
相机/状态 → 模型 → 第 1 个动作
相机/状态 → 模型 → 第 1 个动作
...
每一步都基于最新观察，因此对首次真机更安全：机械臂没按预期移动、物体滑走、相机稍有抖动时，下一步会立即重新观察，而不是继续执行十几步旧计划。
代价是慢。模型每一步都要跑一次，所以实际控制频率取决于：
\[
f_{\text{actual}} \leq \min(f_{\text{client}}, f_{\text{model inference}})
\]即使你 client 设置为 15 Hz，若单次推理需 150 ms，实际也到不了 15 Hz。
它的安全含义也要准确理解：
action_steps=1 减少“陈旧观察导致的连续错误动作”；
它不会限制某一个模型动作本身的大小；
真正的机械安全仍来自本机的 --dry-run、--no-home、--max-step-deg 2、清空桌面和人工监控。
确认动作方向、相机位置和延迟都正确后，再考虑改为 4、8 或 16。
eval_embodiment=so100
这不是普通命令行参数，而是 Hydra 配置覆盖项。
g05-so101 是专门给 SO-100/SO-101 机械臂的权重，但 G0.5 内部把这一类 6 关节机械臂的 canonical embodiment 名称叫作 so100。它会让服务端只保留 SO100/SO101 对应的：
图像槽位定义；
6 维 right_arm 状态与动作；
预处理器；
归一化统计。
所以这里必须是：
eval_embodiment=so100
不是 so101。
model.model_weights_to_bf16=true
将大部分模型权重放入 bfloat16，即 BF16 精度。
FP32 每个浮点数通常 4 bytes；BF16 通常 2 bytes，因此能显著降低模型显存占用和显存带宽压力。A100 对 BF16 有硬件支持，推理通常更合适。
它不意味着所有数值都强制 BF16。代码会在转换后调用：
model.apply_fp32_params()
把需要更高数值稳定性的特定参数保留/恢复为 FP32。
这不是安全开关，主要是推理的显存和速度设置。
model.use_torch_compile=false
这是你问的核心。
PyTorch 正常执行模型时，属于 eager mode：Python 按层、按算子一步步调用 GPU。
Python
  → attention
  → MLP
  → normalization
  → residual add
  → 下一个模块
torch.compile 是 PyTorch 2 提供的图编译/优化功能。启用后，PyTorch 会尝试：
捕获模型实际执行的计算图；
分析张量形状、dtype、算子连接；
融合一部分连续 GPU 操作；
生成更高效的执行代码或 kernel 调度；
后续同形状输入复用已编译结果。
理想情况下，它能减少 Python 调度开销、减少中间张量读写，并提高稳定运行后的吞吐或降低延迟。
但它有三个现实成本：
第一次推理很慢
动态形状或分支可能触发重新编译
报错栈更长、更难判断是模型、编译器还是 CUDA 问题
注意：在这个仓库中，torch.compile(...) 的包装发生在 server 启动时，但真正的大量编译通常在第一条真实推理请求到来时触发。因此你可能看到：
Server 已经 listening
本机发送第一帧
等待明显比后续长
这就是所谓的“首帧编译延迟”。
关闭它：
model.use_torch_compile=false
意味着：
不走图编译
直接用 PyTorch eager mode 推理
稳定运行后的平均速度可能较低，但行为更直接、首次请求更可预期、出错时日志更容易定位。
所以我说“第一次真机更安全”，准确说是工程调试层面的安全：
不会把第一次失败混淆成 compile/CUDA/模型/网络中的哪一层；
不会因为首帧编译等待很久，让你误以为 client 死掉；
能先验证相机、状态坐标、动作方向和 SSH 链路；
成功后再开 compile，性能问题与机器人接口问题就能分开判断。
它不会让模型“更保守”，也不会代替本机的机械臂安全限幅。
当 dry run 和低速真机测试都稳定后，可以重启 server 改为：
model.use_torch_compile=true
此时最好先进行一次 dry run warm-up，让编译发生在不执行动作的阶段。
model.model_arch.attn_implementation=sdpa
指定 Transformer attention 使用 PyTorch 的 SDPA：
\[
\text{Attention}(Q,K,V)
=
\operatorname{softmax}\left(\frac{QK^\top}{\sqrt{d}}\right)V
\]SDPA 即 Scaled Dot-Product Attention。PyTorch 会根据 A100、张量 shape 和 dtype，尽量选择合适的高效 CUDA attention 实现。
用 sdpa 的好处是：
不依赖额外 attention 实现的特殊运行条件；
比较稳，适合第一轮部署；
通常性能也不错。
它同样不是机械安全选项，而是模型内部 attention 的实现选择。

你理解得对：fixed / wrist 是你熟悉的“物理相机角色”；exterior / wrist_right 是 G0.5 模型协议里的“图像槽位名”。两者不是两套相机。
对应关系是：
物理相机	Windows 编号	本机参数	发给 G0.5 的图像键
固定桌面相机	2	FixedCameraIndex / --fixed-camera	exterior
腕部相机	0	WristCameraIndex / --wrist-camera	wrist_right
不存在的左腕相机	无	无	wrist_left，自动发送黑图

所以你不是要再确认一个名为 exterior 的设备；你要确认的是：
编号 2 的真实画面，是否确实是固定在桌面旁、能看到机械臂和物体的广角视角；
编号 0 的真实画面，是否确实是安装在腕部、会随末端一起移动的近景视角。
wrist_right 也不表示“画面右边的相机”；它只是 G0.5 对单臂 SO101 腕部视角采用的标准模型键名。若把两张图反着发送，模型不会报错，但会把“桌面全景”误当成“手腕视角”，效果会很差。

图像有没有裁剪？
有两层，需要分开看。
第一层：本机 → 服务器的原始网络输入。
本机要求两路相机返回严格的：
RGB, uint8, 640 × 480
然后只做：
HWC: 480 × 640 × 3
→
CHW: 3 × 480 × 640
这里没有裁剪、没有缩放、没有翻转、没有 padding；只是把通道维度从最后移到最前，供 PyTorch 使用。
第二层：服务器内部 → 模型输入。
服务器拿到 3×480×640 后，会执行：
torchvision.transforms.Resize([256, 256])
因此图像会直接从：
640 × 480，4:3
缩放为：
256 × 256，1:1
这不是 crop；它会保留整张画面，但会改变长宽比，视觉上相当于压成正方形。之后才做：
\[
x \leftarrow x / 255
\]\[
x \leftarrow (x - 0.5) / 0.5
\]把像素转换到大致 \([-1,1]\) 范围。推理阶段没有训练时的随机颜色扰动或随机裁剪。

MaxStepDeg=2 正常吗？
它是我为第一次真机测试设的保守安全值，不是 G0.5 官方默认值。
它限制的是一次命令相对当前关节状态最多变化多少。client 先计算：
\[
\Delta q = q_{\text{target}} - q_{\text{current}}
\]若某一维的最大绝对变化超过 2，则整个动作向量按比例缩小：
\[
q_{\text{sent}}
=
q_{\text{current}}
+
\Delta q \cdot
\frac{2}{\max_i |\Delta q_i|}
\]因此，一次命令中任何关节都不会被要求跳超过 2。
此外，本机 LeRobot 的 max_relative_target=2 还会再做一层硬件侧保护。两层都在 [g05_so101_policy_client.py (line 100)](D:\\workspace\\Manipulation\\so101\\scripts\\g0.5\\g05_so101_policy_client.py:100) 中。
严格说，名字 MaxStepDeg 对前五个机械臂关节是“度”；夹爪在 LeRobot 内部是 \(0\sim100\) 的开合范围，仍会被同一个数值限制。
它在当前阶段合适，因为：
你还在验证方向、相机槽位、关节坐标转换；
当前 action_steps=1，每步都重新观察；
server 现在单次推理约 1.65 秒，因此真实控制速率远低于 15 Hz；
先慢一些，能把错误控制在小范围内。
确认一小段真实动作方向完全正确后，可考虑逐步试 3，再到 4；不要直接跳到 10。
