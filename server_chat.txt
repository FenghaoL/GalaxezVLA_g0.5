SO101 实际读数
[pan°, lift°, elbow°, wrist_flex°, wrist_roll°, gripper]

        │  G0.5 client 的坐标系变换
        ▼

G0.5 model frame 的 state
[pan°, 90-lift°, elbow+90°, wrist_flex°, wrist_roll°, gripper]

        │  用 g05-so101 的 dataset_stats 做归一化
        ▼

G0.5 模型

        ▼

SO101 client

        ▼
发送给机械臂

elbow_flex	elbow_flex + 90
wrist_flex	wrist_flex
wrist_roll	wrist_roll
gripper	gripper

当前服务传输的是 MessagePack 二进制包；下面用“JSON 形状”展示，便于理解。
最重要的结论：
client 发给 server 的是：图像、当前机械臂状态、自然语言任务。
server 发回来的不是完整模型输出，而是“当前应执行的一个 6 维关节目标”。
服务可以额外带回 cot_text，但没有单独结构化的 subtask 字段。
模型内部一次预测 32 步；server 把它缓存起来，每次只发其中 1 步给机械臂。
1. client → server：发送什么
第一次推理、或 32 步缓存用完时，SO101 client 发：
{
  "images": {
    "exterior":    uint8_array[3, 480, 640],
    "wrist_right": uint8_array[3, 480, 640],
    "wrist_left":  uint8_array[3, 480, 640],  # 没有实体相机时是黑图
  },
  "state": {
    "right_arm": float32_array[6],
  },
  "task": "pick up the red block",
  "embodiment_type": "so100",
  "frequency": 15.0,
}
其中：
图像是 RGB、CHW 排列，不是常见的 HWC；
state.right_arm 是已经经过 signs/offsets 转换后的 G0.5 model frame；
task 是你输入的自然语言；
embodiment_type: "so100" 是选择 SO-100/101 单臂 processor 的内部名字；
frequency=15 表示控制频率。
这些字段由 SO101 client 组装。[client 组包逻辑](/home/fenghao/workspace/GalaxeaVLA/GalaxeaVLA/experiments/so100/so100_policy_client.py)
server 收到后会：

图像从原始 480×640 预处理为模型用的 256×256；
用 dataset_stats.json 归一化 state；
进行模型推理。
验证和内部输入构造在 [serve_policy.py](/home/fenghao/workspace/GalaxeaVLA/GalaxeaVLA/scripts/serve_policy.py)。
2. server → client：真正回什么
每次 server 回的是：
{
  "action": {
    "right_arm": float32_array[6],
  },
  "need_obs": False,
  "cot_text": "..."  # 可选
}
right_arm 的六个数是：
[shoulder_pan, shoulder_lift, elbow_flex,
 wrist_flex, wrist_roll, gripper]
并且已经是：
已从模型内部归一化空间还原；
已从“相对当前 state 的动作”加回当前 state；
因而它是 G0.5 model frame 下的绝对目标位置。
client 随后才把它转换回真实 SO101 的 LeRobot frame，并按 --max-step-deg 限制单步移动，再发送给电机。[接收与执行逻辑](/home/fenghao/workspace/GalaxeaVLA/GalaxeaVLA/experiments/so100/so100_policy_client.py)
所以，server 回的不是“增量动作”，也不是 32×6 的完整数组，而是当前这一小步的 6 维绝对目标。
3. 32 步 action chunk 是怎么工作的
模型内部一次产生未来 32 步：
内部 action chunk: [32, 6]
但你用的 start_server.sh 设置了：
--action_steps 32
所以 server 会：
第 1 次：client 发图像+state → 模型推理 32 步 → server 回第 1 步
第 2~32 次：client 发 {} → server 从缓存回第 2~32 步
第 33 次：client 再发新的图像+state → 模型重新推理
need_obs 就是在告诉 client “下一次是否要重新拍照并发送完整观测”。
need_obs: false：下次只发 {}，继续使用缓存动作；
need_obs: true：下次必须发图像、state、task，重新规划。
这段缓存逻辑写得很明确：server 的函数注释就是“返回单步 action”。[ChunkedPolicyWrapper](/home/fenghao/workspace/GalaxeaVLA/GalaxeaVLA/scripts/serve_policy.py)
